# Organisation branding

The committed application uses the generic **ShutterOS** OS name and original window-and-curtains icon. OS branding is separate from organisation branding. Organisation name, campaign name, and logo belong together in the upper-left organisation block and are supplied locally and must be kept out of version control. “ShutterOS” is a working name and its availability as a product name is not guaranteed.

## Deployment-local organisation logo

The recommended HTTP deployment can take its name and logo from `dist/kiosk-config.json`, without recompilation. Edit these fields in the existing full JSON file, keeping the other required settings:

```json
{
  "organizationName": "Example Organisation",
  "organizationLogo": "logo-organisation.svg"
}
```

Use a filename ending in `.png`, `.webp`, or `.svg`, with only ASCII letters, numbers, dots, `_`, and `-`. Paths, URL schemes, query strings, fragments, and data URLs are rejected. Place the image beside `kiosk-config.json` and the generated `index.html`; when building from source, put it in `static/` so the static adapter copies it to `dist/`. The browser loads it only as an `<img>` resource. Keep the file at or below 256 KiB. Use a self-contained SVG with a `viewBox`; external fonts or images should not be required. The image keeps its proportions inside a maximum height of 54 px and maximum width of `min(160px, 26vw)`. A missing or unreadable logo falls back to the organisation initials.

```text
dist/
  index.html
  kiosk-config.json
  logo-organisation.svg
  ...other generated site files
```

`dist/` is ignored by Git and regenerated by every build: keep your organisation files in a separate local backup. `static/logo-organisation.*` is also ignored for an optional customised source build. Any other custom filename needs its own ignore rule. Editing only the deployed JSON does not change the portable artifact.

The portable build reads `static/kiosk-config.json` and embeds the named image as a data URL in `dist/portable/shutteros.html`. A configured portable logo that is missing, too large, outside `static/` through a symlink, or inconsistent with its PNG/WebP/SVG filename makes the build fail. Rebuild the portable file after changing either the JSON or image.

## Optional private build-time branding

For a build that also customises the OS name or campaign label, create `private/branding.json` and place the logo file under `private/`:

```json
{
  "applicationName": "ShutterOS",
  "organizationName": "Example Organisation",
  "campaignName": "Security Week",
  "organizationLogo": "private/logo.png"
}
```

Keep `applicationName` (the OS name) distinct from `organizationName` (the organisation shown in the organisation block). This optional build-time logo accepts PNG or WebP of at most 256 KiB; use the deployment-local method above for SVG. `pnpm dev`, `pnpm check`, `pnpm build`, and the Storybook commands automatically prepare the branding. The script validates the name, resolves symlinks, checks that the logo remains inside `private/`, verifies magic bytes, and writes the ignored `src/lib/branding.generated.ts` data module with an embedded base64 data URL. No remote URL is accepted. The composition root imports the generated module and passes its values as props. The organisation block is rendered once per screen, at the upper left of login and desktop; the OS symbol remains independent. Without private configuration, the build uses the generic ShutterOS identity.

Keep `private/branding.json` and `private/logo.*` outside version control. This project is personal MIT software; private brand assets remain with the deploying organisation. The generated module is also ignored and must be regenerated on each clean checkout. Do not put real passwords, credentials, or other secrets in branding files.

Private build-time branding has precedence over deployment-local branding. The order is the private `organizationLogo` from `private/branding.json`, then the portable embedded image when applicable, then the filename from `kiosk-config.json`. This keeps an explicitly customised private artifact stable while allowing a generic static deployment to replace its local organisation file without rebuilding.

## Public and private artifacts

A customised build contains its organisation name and embedded logo in the generated HTML/JavaScript. Ignoring the source files does not remove them from that build. Publish only a generic build from a clean checkout to the personal public demo. Review staged files before committing; `.gitignore` does not exclude a file that is already tracked or force-added.
