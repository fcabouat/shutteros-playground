# Organisation branding

[Français](branding.fr.md)

**ShutterOS** is the fictional OS identity, with its window-and-curtains icon. The campaign label and organisation identities appear together in the game bar on the welcome screen, login and desktop. Supply organisation assets locally and keep them out of version control. See [licensing and attribution](legal.md) for ownership and redistribution terms.

The organisation logos appear on the left, followed by a separator and then the campaign label. With two organisations, both logos align on the same row. Each logo keeps its proportions within a 52 px-high area in the 64 px bar, leaving a 6 px margin above and below.

When a logo loads successfully, its organisation name is visually hidden by default to keep the bar compact. The name remains available to screen readers and in a tooltip. Without a logo, or if the image cannot be loaded, the name is shown. Private build-time branding can force names to remain visible beside valid logos; see `showOrganizationNames` below.

With no organisation fields configured, the public demo displays **Votre organisation** / **Your organization**, following the selected language. A second organisation is optional and shares the same identity block.

## Deployment-local organisation logos

The recommended HTTP deployment can take its name and logo from `../shutteros-build/dist/kiosk-config.json`, without recompilation. Edit these fields in the existing full JSON file, keeping the other required settings:

```json
{
  "organizationName": "Example Organisation",
  "organizationLogo": "logo-organisation.svg",
  "partnerOrganizationName": "Partner Organisation",
  "partnerOrganizationLogo": "logo-partner-organisation.svg"
}
```

Omit both `partnerOrganizationName` and `partnerOrganizationLogo` for a single organisation. Either organisation may use a name without a logo; a partner logo requires its partner name. Omit `organizationName` to retain the translated placeholder.

Use a filename ending in `.png`, `.webp`, or `.svg`, with only ASCII letters, numbers, dots, `_`, and `-`. Paths, URL schemes, query strings, fragments, and data URLs are rejected. Place the image beside `kiosk-config.json` and the generated `index.html`; when building from source, put it in `static/` so the static adapter copies it to `../shutteros-build/dist/`. The browser loads it only as an `<img>` resource. Keep the file at or below 256 KiB. Use a self-contained SVG with a `viewBox`; external fonts or images should not be required. Each image keeps its proportions within the 52 px logo height. The controls wrap responsively when space is limited. A missing or unreadable logo shows that organisation’s name instead.

```text
../shutteros-build/dist/
  index.html
  kiosk-config.json
  logo-organisation.svg
  logo-partner-organisation.svg
  ...other generated site files
```

`../shutteros-build/dist/` is outside the source checkout and regenerated by every build: keep your organisation files in a separate local backup. `static/logo-organisation.*` and `static/logo-partner-organisation.*` are also ignored for an optional customised source build. Any other custom filename needs its own ignore rule. Editing only the deployed JSON does not change the portable artifact.

The portable build reads `game` from ignored `private/configuration.json` when present, otherwise `static/kiosk-config.json`, and embeds named images as data URLs in `../shutteros-build/dist/portable/shutteros.html`. A configured portable logo that is missing, too large, outside `static/` through a symlink, or inconsistent with its PNG/WebP/SVG filename makes the build fail. Rebuild the portable file after changing either the JSON or image.

## Optional private build-time branding

Use one ignored `private/configuration.json` for branding and game settings; place logo files under `private/`:

```json
{
  "applicationName": "ShutterOS",
  "organizationName": "Example Organisation",
  "campaignName": "Security Week",
  "organizationLogo": "private/logo.png",
  "showOrganizationNames": true
}
```

The private file also accepts optional `partnerOrganizationName` and `partnerOrganizationLogo` (a path under `private/`). Set `showOrganizationNames` to `true` to keep both organisation names visible even when their logos load successfully. It defaults to `false` and is available only in `private/configuration.json`, not in `kiosk-config.json`.

To customise contacts and simulation details, add a `game` key to the same object with a **complete** version 1 object copied from `static/kiosk-config.json`, then change its local values. Without that key, the build uses the tracked generic default. Local builds copy this nested object to `../shutteros-build/dist/kiosk-config.json` and embed it in portable HTML. `pnpm verify` and `pnpm build:site` use only public defaults. Game login phrases must be fictional, never real credentials or operational secrets.

Keep `applicationName` (the OS name) distinct from `organizationName` (the organisation shown in the organisation block). This optional build-time logo accepts PNG, WebP or SVG of at most 256 KiB. SVG files must be self-contained, as for deployment-local logos. `pnpm dev`, `pnpm check`, `pnpm build`, and the Storybook commands automatically prepare the branding. The script validates the name, resolves symlinks, checks that the logo remains inside `private/`, checks image format, and writes the ignored `../shutteros-build/generated/branding.generated.ts` data module with an embedded base64 data URL. No remote URL is accepted. The composition root imports the generated module and passes its values as props. The organisation block is rendered once per screen, at the upper left of welcome, login and desktop; the OS symbol remains independent. Without private configuration, the build uses the generic ShutterOS identity.

Keep `private/configuration.json` and `private/logo.*` outside version control. This project is personal MIT software; private brand assets remain with the deploying organisation. The generated module lives outside the source checkout and must be regenerated on each clean checkout. Do not put real passwords, credentials, or other secrets in the configuration.

Private build-time branding has precedence over deployment-local branding. The same precedence applies independently to both organisations. The order is the private `organizationLogo` from `private/configuration.json`, then the portable embedded image when applicable, then the filename from `kiosk-config.json`. This keeps an explicitly customised private artifact stable while allowing a generic static deployment to replace its local organisation file without rebuilding.

## Public and private artifacts

A customised build contains local identities and contacts in the generated HTML/JSON/ISO. Ignoring the source file does not remove them from that build. The generated artifacts stay under `../shutteros-build/`, outside the public checkout. `pnpm build:site` selects the public defaults for the public demo. Review staged files before committing; `.gitignore` does not exclude a file that is already tracked or force-added.

`private/` is reserved for local build configuration and its images. ISO caches, operator credentials and VM files belong under `../shutteros-build`. `pnpm kiosk:iso` rebuilds with the current local configuration; its strict `--skip-build` option requires matching build metadata and does not silently accept an old public build.
